Findings

  1. Root cause. Claude Code prefers ANTHROPIC_AUTH_TOKEN to apiKeyHelper. On a 401 it retries 11 times over about 3 minutes and prints nothing in -p mode. The old installer ran that test with no limit, so it looked hung (A1). Every everyday request failed the same way (A2).
  2. Other software can steer claude-lcls in two more ways. CLAUDE_CODE_USE_BEDROCK=1 from another tool's setup left a request unanswered (A3). A repo's .claude/settings.json switched opus to Opus 5 (A4). Both are closed now (C2, C4).
  3. Still open by design: a token pasted into ~/.claude-lcls/settings.json still wins, because it never passes through the environment. The docs describe that form for hand setups, so the installer warns rather than deletes (G1). Cogito reads the same file.
  4. Escape hatches work: CLAUDE_LCLS_KEEP_ENV keeps a named variable on purpose (C5). A user's own --settings replaces the shared file, because Claude Code keeps only the last one (measured before this run, not re-run here).

Not covered

  • The installer's interactive prompts (pasting a personal key, choosing a passphrase). Every installer run here was unattended (</dev/null). The client's paste happened before the step that hung, and the key step is unchanged by this branch.
  • The live publish. The launcher and shared settings ran from the branch clone. The publish tool ran only against a mock deploy root (J1–J3).
  • Cogito sessions, and macOS or laptop installs.

Audit trail

Before the take. One unrecorded smoke run of the branch installer in a poisoned throwaway home, to catch installer bugs before recording. It passed (whole run 3 s, then claude-lcls -p on Opus 5.5). Its home was deleted.

What was typed into the recording. Everything was sent by the agent with tmux send-keys; no human typed in the pane. The export line, bash proof.sh, bash recheck.sh, the chapter K commands, and in the interactive session: Enter (theme), Enter (security notes), Down and Enter (trust /tmp, written to the throwaway config only), the prompt, /exit.

First-pass failures. A4, E1 and H1 failed for reasons in the test script, explained under each row. They stay in the table. After the first summary the take sat idle for about 100 s while their evidence was read (shortened in playback). Chapter R re-ran them correctly in the same take. proof.sh was then corrected (A4 uses a home without the token, E1 greps exact strings, H1 uses a gateway that never answers) and re-run end to end, unrecorded: 24 of 24 PASS (sdfiana024, 10:03–10:07 PT, saved as checks-rerun.tsv).

Redaction. The installer prints the last 4 characters of the shared key as (…XXXX). Those were replaced with …**** in the recording and the logs (7 places), on the S3DF side, by the converter script. It also checked that the full key appears nowhere. The account's name and SLAC email, which the installer printed when it made a GnuPG key for each throwaway home, were masked the same way (8 places) by tools/proofs/mask.py before the page went public.

Throwaway state and cleanup. Each case ran in a throwaway home under node-local /tmp/lcls-proof.* (mode 700) with its own GNUPGHOME. Each home held a copy of the shared key in its pass store and key.dat. The mock deploy root lived in the same folder. After the take and the re-run, every throwaway home was deleted and its GnuPG agent stopped. The demo tmux server was stopped. Raw logs holding the unmasked last 4 characters were deleted; the masked copies were kept. A final scan found the full key in 0 files under the proof folder.
